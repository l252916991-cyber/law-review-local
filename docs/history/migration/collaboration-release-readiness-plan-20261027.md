## 4. R1：落实角色与实际权限的交集

统一使用服务端有效权限判断：保留现有管理员规则；普通成员须同时满足成员权限、案件角色、案件授权和动作关系条件。角色不能恢复已经撤销的成员权限。

| 动作 | 所需权限 | 附加业务条件 |
|---|---|---|
| 创建/提交报告 | `edit` | 当前案件可访问，状态允许提交 |
| 报告退回/批准/作废 | `approve` | 承办或复核角色，状态允许操作；退回原因必填 |
| 正式下载报告包 | `export` | 案件可访问、指定报告已批准、来源依据仍有效 |
| 创建/分派任务、调整期限、取消任务 | `edit` | 承办角色或管理员，状态允许操作 |
| 开始/提交任务 | `edit` | 当前指派人或承办，任务未关闭 |
| 退回/完成任务 | `approve` | 承办或复核角色，状态允许操作 |

实施时沿用既有任务创建规则核对动作入口，明确上述约定与现有行为的差异，不把前端按钮显隐当作授权。环境配置身份没有案件角色时的行为须单独写入权限矩阵，不通过空角色默认授予复核能力。

验收重点：目录成员仅剩 `view`、保留 `reviewer` 或 `owner` 时，直接请求 API 仍被拒绝；只撤 `approve` 不撤 `view` 时既有会话能查看但不能复核；有 `approve`、无 `edit` 的复核律师仍能批准，不能编辑正文。跨案拒绝、停用、令牌轮换和合法复核均保持通过。任务操作者权限改变后也按当前权限检查，不沿用任务创建时权限。

## 5. R2：批准绑定冻结正文，导出使用同一版本

### 5.1 冻结对象

采用**冻结待审交付对象**的方案。报告准备阶段明确模板和纳入内容，提交复核前生成可预览的不可变正文版本。批准绑定该版本及其内容哈希，正式导出读取指定 `report_id` 的冻结内容。

冻结范围至少包含：

- 模板 ID、模板完整区块和静态正文、渲染器版本；仅保存模板 ID 不足以识别模板修改。
- 案件摘要字段、材料目录、证据内容及来源、审批归属。
- 纳入报告的问答正文、顺序、会话标题与署名；明确纳入范围，不在下载时自动追加新问答。
- 全量资金流水及其顺序、条数、币种和内容摘要，保留超过 500 条的回归。
- 所选附件的受控路径、文件名、大小与内容摘要，以及生成正文的文件清单。

正文摘要与批准元信息分开计算，避免把批准时间、批准人或最终 ZIP 哈希放进自身摘要造成循环。最终包清单同时登记报告版本、正文摘要、来源依据摘要、批准记录和实际文件摘要。

### 5.2 一致性与变更规则

1. 案件、材料、证据、问答、流水和模板来自同一个明确的一致性读取边界。正文生成和附件复制不得长时间占用写锁。
2. 文件在受控临时位置冻结并核对摘要；冻结未完整成功的草稿不能送审。附件缺失、复制期间内容变化、磁盘不足或摘要不一致必须明确失败，不生成“已就绪”标记。
3. 审批只作用于复核人实际预览的冻结版本，并再次检查当前来源依据。报告流转使用预期 `row_version` 和状态条件更新；并发批准/退回只能有一个成功，其余返回冲突，事件不可重复。不得审批后重新从活动表拼接正文。
4. 沿用材料变化需重审的规则：案件信息、材料正文/目录、证据及纳入的流水发生相关变化时，正式导出拒绝复用旧批准；重新冻结并审批新版本。
5. 同一模板的区块或静态正文变化也触发重审。沿用当前 `qa_log` 包含全案问答的范围时，新增、修改或删除问答均使依据过期；未选择问答区块的报告无需依赖无关聊天。任何新内容都不能自动进入旧批准包；旧冻结对象可按权限查阅，当前正式交付须生成并审批新版本。
6. 正式导出以明确的报告版本为目标，不能独立传入另一个模板替换正文。若为兼容保留 `template_id`，不匹配时拒绝，不默默覆盖。
7. 候选包生成后，在最终交付登记前重新检查案件访问与导出权限、报告状态/版本和来源依据，登记正文摘要、包摘要及批准版本后才允许正式下载；期间作废报告、撤权或依据变化须拒绝。不把静态工件路径作为绕过授权的公开下载地址。记录明确的校验/交付时点，已经发出的字节不宣称可追溯撤回。并发变更的可观察结果须为“完整冻结版本”或“拒绝并要求重审”，不得混合版本。

### 5.3 页面、迁移与存储

- 页面顺序：选择模板及内容 → 准备草稿 → 查看冻结预览 → 提交复核 → 批准/退回 → 下载指定批准版本。显示版本、来源范围、失效原因与复核意见。
- schema 按实施时的 `SCHEMA_VERSION` 顺序新增迁移；当前为 25，下一版本暂按 26 设计，遇其他已合入迁移时顺延。不得修改既有迁移、手工降低版本号。
- 旧报告不具备完整冻结正文。保留历史批准人、事件及记录，但不能用当前内容自动补哈希并宣称旧审批覆盖它；正式交付前必须重新准备和审批。
- 冻结工件放在受保护的数据目录，命名、访问和备份清单受控；规划空间预算及保留规则。不在本批自动清理历史工件。中断工件可识别，恢复后不能被误当成已批准报告。
- 同步备份/恢复的工件覆盖和路径迁移测试，禁止新增工件游离于恢复单元之外。

## 7. M1：旧库副本迁移与恢复

当前已知本机业务库记录为 v13；本计划不直接访问或升级该库。执行前由维护者登记实际源目录、数据库版本、独立 checkpoint 路径、保管配置、停写窗口和获准案件范围。

1. 排空在途任务，停止 API 与 worker，确认没有进程继续写入。保留原始数据及匹配旧版本程序。
2. 用独立快照工具备份并校验旧库。当前协作验收脚本的六表计数假设新表存在，不能直接当作旧 v13 库的前置备份入口。
3. 将快照恢复到新的私有目录。源、备份和恢复目录互不嵌套；备份/恢复目标必须不存在。

```sh
# 仅为操作模板；使用已登记且获准的路径，先完成停写。
uv run --locked python scripts/data_snapshot.py backup \
  --data-dir /absolute/private-source \
  --output /absolute/private-backups/before-upgrade \
  --checkpoint-db /absolute/actual-checkpoints.sqlite --quiescent
uv run --locked python scripts/data_snapshot.py verify /absolute/private-backups/before-upgrade
uv run --locked python scripts/data_snapshot.py restore /absolute/private-backups/before-upgrade \
  --output /absolute/private-restored-copy
```

没有独立 checkpoint 时按实际情况省略 `--checkpoint-db`；有自定义路径时必须显式传入，底层工具不自动读取该环境变量。密钥、`.env` 和 Redis 不在该备份中，另行受控保管；不要把凭证复制到仓库或测试报告。

4. 按 `RESTORE_REPORT.json` 的 `checkpoint_env` 配置新进程。备份含 checkpoint 时，恢复位置为新目录下 `langgraph_checkpoints.sqlite`；`LAW_REVIEW_DATA_DIR` 和 checkpoint 都必须指向副本，不得继续指向原库。副本使用独立端口、队列和测试身份，先禁止模型及外部服务调用。
5. 用当前交付候选启动副本完成顺序迁移到最终 schema。验证迁移失败时事务回滚、重复启动不重复迁移；覆盖 v13→最终版本及 v25→最终版本，旧批准记录按 R2 保留历史且不能冒充完整签发。
6. 核对完整性、外键、迁移前后关键数据/归属、原件摘要、历史审批、事件、任务、报告、会话与 checkpoint。启动还会恢复中断任务、清理过期会话和维护全文索引，预期差异逐项登记；新增系统表不要求与旧库机械等量，原业务数据不能无说明丢失。
7. 在副本上跑五身份业务链，再对升级后的副本停写备份、恢复到第二个新目录，启动恢复实例复验。新冻结报告工件及其权限、摘要和下载也必须恢复可用。
8. 演练回滚使用匹配旧程序及迁移前快照恢复到新目录，不降低 `user_version`，不把新版本库交给旧程序直接运行。记录恢复耗时及升级后新增写入如何保留/转交，不能默认回滚不丢新数据。

只有副本演练通过并安排实际维护窗口后，才执行正式库升级。`--quiescent` 是操作者声明，不能代替停写检查；任何 `INCOMPLETE`/`RESTORE_INCOMPLETE` 目录不得启动。

## 8. U1：验收用例与证据

自动化先使用合成数据，目标设备人工验收使用获准样本。管理员、承办律师、复核律师、助理、只读人员使用独立身份和会话；成功链路不能全由管理员代跑。

| 编号 | 场景 | 必须观察到的结果 |
|---|---|---|
| A01 | 仅 `view` 的成员保留承办/复核角色，直接调用报告及任务复核 API | 拒绝越权，无状态变更；合法复核人仍成功 |
| A02 | 已登录人员撤去审批权限、停用或轮换令牌 | 分别表现为操作被拒或会话失效，历史审计保留 |
| A03 | 只读或未授权人员尝试跨案查看、下载、导出及直接访问冻结工件 | 服务端拒绝，无内容泄露 |
| A04 | 两人持旧版本保存同一证据/材料；随后复核 | 冲突明确，先保存内容保留，批准归属正确 |
| A05 | 任务指派→开始→提交→退回→重新提交→完成 | 原因、责任人、期限和追加事件一致，关闭后不能越权重开 |
| A06 | 选模板、冻结预览、送审、批准、指定版本导出 | 预览与包内正文摘要一致，清单对应同一报告及批准人 |
| A07 | 批准后切换模板、改静态正文，含问答的报告新增/删除问答 | 模板不匹配或依据过期时拒绝正式交付；新内容须新版本审批 |
| A08 | 送审/批准后修改材料、证据或纳入流水 | 拒绝批准或正式交付，提示重新准备与复核 |
| A09 | 用同步屏障控制导出读取期间另一个连接修改材料/批准新版本，或在交付登记前作废/撤权 | 输出完整且有效的指定冻结版本或明确失败；不出现混搭或越权成功登记 |
| A10 | 超过 500 条流水、多个币种、附件缺失/变动 | 全量条数与哈希一致，币种口径明确；缺件或摘要错误阻断冻结/交付 |
| A11 | 冻结中断、磁盘不足、恢复后缺冻结工件 | 未完成工件不可批准或下载，错误可诊断，不伪造成功 |
| A12 | v13 与 v25 副本迁移、迁移故障、重复启动、恢复后启动 | 数据和历史归属保留，故障事务回滚，恢复业务可操作 |
| A13 | 目标设备的真实模型、扫描 PDF/图片 OCR、材料不足问题 | 实际推理/解析成功且能回原页；失败和不确定性明确，由律师核对结果 |
| A14 | 目标人数的读写、模型任务与批量导入并发 | 在事先登记阈值内完成；无静默丢写、越权、数据损坏或未解释失败 |
| A15 | 备份失败、模型不可用、磁盘阈值、队列无消费 | 负责人能通过已部署的巡检/告警或值班流程发现并处理，记录发现与恢复时间 |

A01–A12 应有与风险相匹配的自动回归及实际页面/进程验证；并发用例使用可重复的同步控制，不依赖随机 sleep。A13 的法律业务效果由独立复核人记录，引用可定位、单元测试通过或模型 `/models` 可访问均不能代替该结果。付费或远端模型调用按具体授权范围执行。
