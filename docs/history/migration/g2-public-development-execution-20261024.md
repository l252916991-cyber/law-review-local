## 4. 公开文本适配修正与复验

首轮逐题归因发现，采集适配器只识别 `〖基本案情〗` 等标记，没有识别实际网页的 `【基本案情】`、`【裁判结果】`。部分整案文字被合为单页；查询片段可能优先截到开头，后文已存在的金额或凭证类型没有进入模型上下文。首轮 `training-court-refund` 因此误拒，其他三个回答存在未答全所问的问题；完整记录见 `comparison-02/developer-review.json`。

修正仅作用于私有公开文本适配器：识别两种括号和劳动仲裁栏目；按统一标点边界切为最多 144 字符的逻辑块，不依赖问题、预期、金额或答案关键词。校验原案例全部非空白字符拼接后完全一致，没有删除或补造正文。新快照是不同的数据身份，不将新旧批次的来源编号、结果或 p95 混合计算。

适配器自检覆盖两种括号、劳动栏目、长段末尾证据保留、无标点长段及空文本。六个案例均校验无损、逻辑块上限和完整来源摘要；旧十二题的题面与预期逐项保持一致。复验中原退款题已正确回答，支付凭证类型与竞业报告材料列表也已答全。

完整逐句开发自审后，仍有两项问题：

- `training-facts`：候选只说培训费缴纳和地点变更“均明确记载”，没有给出具体支付或变更事实；同快照的原生对照给出了金额和地点变更经过。合法 JSON、真实引用及 supported 状态不能证明已回答原问题。
- `noncompete-arbitration-result`：第一项正确写明驳回公司全部请求；第二项又摘录付款诉求却没有说明这是公司的仲裁请求，容易将当事人诉求与裁决结果混淆。引用片段真实，表述角色仍需修正。实际问答与原文只保存在私有证据目录。

最终开发内容自审以私有 `final-developer-review.json` 为准（16/18），它补充并取代初步按锚点汇总的 17/18 计数；自动行为检查仍为 18/18。此为 Codex 自审，不是独立或专业律师终评。保留 `semantic_entailment_checked=false`。

## 5. 历史结果复用缺陷修复

十八题后使用全新宿主与实际框架进程复用已完成的成功/拒绝结果时，发现 `app/integration/host_integration.py` 无差别拒绝 deadline 之后收到的 succeeded 结果，连已在宿主保存的原成功也被误判为晚到完成。

修复保留当前授权、来源、版本、artifact 和 trace 校验；只有宿主已经是 succeeded 且框架返回结果与原保存结果完全一致，才允许在 deadline 后读取/恢复/重建投影。不刷新 deadline，不放行新的晚到成功，也不接受不一致的历史结果。

新增五项回归：历史成功的 recover/inspect/rebuild 三项；历史结果不一致仍拒绝；首次成功晚到仍为 unknown、待对账。修复前 **3 failed / 2 passed**，修复后受影响模块 **44 passed**。公开案例成功与业务拒绝的全新进程复用也已通过：原 run/framework run/result 不变，调用、消息、步骤和回执未增加；provider/compute 派发守卫触发 0 次。

三十次 9B 模型评估发生在该修复之前，不能描述为修复后全量模型复验；该修复没有改变生成、检索或提示，最终代码另行接受完整离线和实际历史结果复用验证。原 507 的 unknown 不因该修复变成成功或已对账。
