## 1. 当前起点与目标

R2 实施记录确认 E09/E10 的适用框架契约及 E11/G3 通过，律所已精确绑定 ForgeHarness 0.8.3。框架 92/92 门禁、源码和干净副本各 1178 测试通过；宿主 Python 3.11/3.12/3.14 各 828 通过、3 项既有跳过。这些是上一批证据，本计划编制时没有重跑业务测试。

## 4. 必须固定的设计规则

### 4.1 六类写入与回执

六类动作保持现有枚举：`run_record`、`step_record`、`gap_detection`、`memory_draft`、`conversation_message`、`audit_entry`。逐类列出合法字段、实际业务权限、源版本、稳定逻辑动作 ID、摘要及事务范围。

幂等键绑定可信主体、案件范围、动作和规范化请求身份；不得用重试次数或进程随机 ID 生成新的业务动作。同键更换内容、主体、范围或源版本时按绑定规则拒绝，不泄露原结果。`query_receipt` 也重新授权。重复查询/提交不重复产生业务消息、记忆草稿或对应业务审计。

业务效果与可查询回执在宿主同一事务持久化。框架 journal/checkpoint 与宿主事务之间通过回执、重试投影及对账收敛；丢响应不能推断写入失败。查询无记录时还须核对调用准入/在途事实，只有证明安全才能重试；未知效果或费用继续保持待对账。

框架执行批准与律师对证据的业务批准分别建模，保持既有业务审批语义，不给原本允许的内部保存一律增加人工批准。

### 4.2 映射、事件与恢复

框架持久状态是执行事实来源；宿主保存可重建业务投影、请求关联与回执，不实现第二套节点调度器。宿主配额按持久任务状态重建，重复完成、取消或重启只释放一次；未明副作用不因清理配额而丢失对账责任。

新持久事件明确追加序号、游标和事件 ID；允许至少一次投递并去重，乱序到达不得使终态倒退。既有 RunEvent v2 的内容摘要只能标识快照修订，不能作为时间顺序。发生协议语义变化时升版并保留历史读取适配。

恢复按保存的运行时/编排/协议版本路由，重新核验主体授权、资料版本、模型身份、预算和原绝对 deadline。未知版本拒绝，不自动换旧运行时重跑。审批等待计入时限；取消接受、执行停止与副作用完成分别留存。

保持单 Web、≤2 后台任务及准入 4 的工程范围。R2 的分支/join 持久语义不代表外部调用并发或分布式吞吐已经验证。

### 4.3 schema 与生命周期

采用增量迁移、明确唯一约束和历史读取方案，迁移前后及重复启动均验证；记录旧代码对新 schema 的拒绝边界。投影重建不能再次执行业务动作。

案件撤权、归档、删除与保留规则覆盖宿主映射、回执、框架状态及投影；先核对现有政策，不把删库当作恢复手段。正式备份恢复和当前 schema 兼容回退的完整演练留 E18。

| --- | --- | --- |
| H-A01 | 六类动作首次及重复提交 | 各一份预期业务效果；回执稳定可查；重复标记符合现有契约 |
