# 行级安全（信息隔离墙）开销基准（2026-11-02）

结论：在 PostgreSQL 上，信息隔离墙由行级安全（RLS）执行。对没有被挡在任何墙外的用户（绝大多数请求），10,000 页单案向量检索 p50 从 51 ms 变为 67 ms；对被挡在墙外、库里五分之四的材料都对他隐藏的用户，p50 为 104 ms。两种身份 30 个查询的前 20 页都与超级用户结果完全相同。策略写法改过两次，第一版的开销是现在的近三倍。

原始结果：[postgres-rls-overhead-20261102.json](postgres-rls-overhead-20261102.json)；复现命令：

```sh
uv run --locked python scripts/benchmark_vector_search.py \
  --postgres "host=127.0.0.1 port=55432 user=postgres dbname=postgres" \
  --pages 10000 --cases 5 --queries 30 --rls
```

## 条件

与[页向量检索基准](postgres-vector-search-20261102.md)相同：云端开发容器 2 vCPU、7 GiB，PostgreSQL 16.15 + pgvector 0.6.0 同机，5 个案件 × 10,000 页合成数据，384 维哈希向量，被测函数是 `app/search_backend.py` 的 `scored_page_vectors`（统计不兼容向量 + 排序两条语句）。

`--rls` 另建一个归非超级用户角色 `lexvault_app` 所有的库，装入同样的数据，给案件 2–5 设墙（墙内只有"其他律师"），然后在案件 1 内检索：

- **墙外身份**"基准律师"：4 个案件对他隐藏，即 40,000 页；
- **墙内身份**"其他律师"：没有案件对他隐藏。

超级用户的结果是对照组（超级用户不受行级安全约束）。

## 结果

| 身份 | p50 | p95 | 与对照组前 20 页一致 |
| --- | --- | --- | --- |
| 超级用户（对照） | 51 ms | 65 ms | — |
| 应用角色，没有案件被隐藏 | 67 ms | 82 ms | 30/30 |
| 应用角色，4 个案件被隐藏 | 104 ms | 124 ms | 30/30 |

## 策略写法的三版

同一组数据、同一个墙外身份，只改策略写法：

| 版本 | 写法 | 墙外 p50 | 对照 p50 | 问题 |
| --- | --- | --- | --- | --- |
| 1 | 每行调用 `lexvault_case_visible(case_id)`，子表经父表逐层调用 | 286 ms | 66 ms | 函数逐行执行，每行都查一次墙表 |
| 2 | 隐藏案件编号每条语句算一次；子表写成 `page_id IN (SELECT id FROM pages)` | 347 ms | 66 ms | 每条语句都要扫完整张父表来建哈希；规划器估不准行数，选了嵌套循环 + 物化，连接条件被执行约 100 万次 |
| 3（现行） | 隐藏案件编号每条语句算一次；子表写成 `EXISTS (SELECT 1 FROM pages p WHERE p.id = embedding_cache.page_id)` | 104 ms | 51 ms | — |

第 3 版的执行计划：先按案件取材料和页，再按主键逐页取向量，每取一行用主键回查一次父表。开销跟查询实际碰到的行数成正比，与库里其他案件有多少数据无关；第 2 版则随整张父表增长，库越大越慢。没有案件被隐藏时，策略第一项 `cardinality(...) = 0` 直接成立，不碰父表。

## 边界

- 单次测量，同机无网络往返；不同轮次之间对照组本身在 48–66 ms 之间波动，比较看同一轮内的比值。
- 墙外场景是刻意放大的：五分之四的材料对一个人隐藏。实际律所里设墙的案件是少数。
- 应用角色的计划没有用上并行工作进程，超级用户的计划用了 1 个。这可能是没有案件被隐藏时仍多出约 16 ms 的原因之一，未单独验证。
