# D01：领域节点持久接入设计

日期：2026-10-23。对应[计划](domain-integration-plan-20261023.md) D01–D05。实现、验证及自审为 Codex，专业评审未执行。

## 1. 已确认范围与分层

用户已确认每案 500 页、正文 200 万字符，超限拒绝；单页、检索包和法条语料继续按 E03。实际模型只允许合成材料调用已有本机服务，无外发、付费或真实案件授权。正式路由保持到 E14 的原依赖门槛。

保留 `forgeharness-isolated-v1` 合成图及其 wire v2、写回执 v1。新增独立 `forgeharness-domain-isolated-v1` 领域候选，使用领域图 v1、wire v3、领域写回执 v2，仍只接受排他新建并显式标记的隔离数据库。复用同一事务/回执、受理、lease、事件投影和一次性启动授权机制，不复制节点调度器。框架仍为精确 0.8.3，追加事件继续使用 host_event_version=1；原公共 RunEvent v2 的快照语义不变。

D05 的生产候选须另有受信部署配置与准入边界，并在隔离验收库验证；不能把“生产容量确认”解释为给当前业务库添加合成标记的授权。正式 `RuntimeControl`、后台、HTTP/UI 接线留 E14/E15。

## 2. 固定图与节点输入输出

首次受理按当前 `PlannerAgent.build_plan` 冻结路由和完整图，图摘要、实际框架/wheel、主体、输入和绝对 deadline 一并绑定。恢复只读取保存的图，不重新规划。现有 planner 为确定性规则规划器；以后若改为模型规划，须另处理该模型调用的持久窗口。

| 节点 | 输入及前驱 | 持久结果 / 效果 |
| --- | --- | --- |
| user-message | 受理的固定问题 | 唯一 user 消息及回执 |
| planner | 固定问题与计划 | 原路由、PlanNode 定义；一条领域步骤 |
| memory_recall | planner、当前授权输入 | 固定已验证记忆结果；不召回本轮 runtime_draft |
| retrieve | memory_recall | 页级检索结果、来源/页码/引文、检索指标 |
| facts / evidence | retrieve | 当前原领域算法的 schema 校验输出 |
| contradiction / statutory_conflict / gap_detection | 固定计划中的对应依赖 | 条件节点输出；法条独立绑定语料，不伪装案件页 |
| specialist-join | 所有适用专家 | 框架零调用预算 join，宿主不调度节点 |
| critic | specialist-join | 规则汇总；真实模型由受控模型步骤独立处理，不混入不可查的业务写入 |
| finish | critic（及实际模型步骤，若配置并实现） | 严格引用答案、引用列表、页面包、法条来源及验证结果；完成前验证不足则拒绝 |
| persist-effects | finish | 缺口待核验、可选 runtime_draft、最终 assistant 消息；每项稳定子动作键 |
| audit | persist-effects | 业务审计及严格答案；作为最终工具节点，框架再执行来源 verifier |

节点计算在授权的私有快照内执行，复用 `ReadonlyCaseSession` 的原专家、检索、Critic 与来源构造。源库中的 run/步骤/消息/缺口/草稿输出不成为自己的输入版本。每次新快照过滤该候选生成的 run、缺口及 runtime_draft，再按保存的当前输入版本核对；历史源记忆仍保持原语义。

## 3. 无内存依赖的恢复

完成节点的输出保存到 `agent_steps.output_json`，其效果摘要绑定不可变回执。后续回调先重新授权并核对源版本，再按稳定框架调用键查询前驱步骤回执、检查效果摘要，加载原输出。恢复可以重建临时快照和内存容器，但不得重算已完成节点或重发已完成模型调用。

保存的 graph_json 包含固定节点名、依赖、动作类型及请求参数；不接受 pipe 给出的 SQL、数据库路径、主体或任意 payload。动态领域输出只能由宿主按已登记节点计算与校验，计算后再在写事务内核对取消、deadline、源版本和前驱效果身份。

每个节点的步骤结果及其相关子效果在宿主一个事务中提交。查询到主步骤回执即应能证明相关子效果；查询时逐项核验子回执/效果。事务前退出，无回执但已派发仍保持 unknown；事务提交后丢响应，可信 resolver 读取相同输出与回执完成对账。结果变化不能用原键覆盖。

运行完成投影保存答案与引用，只有框架 verifier 通过才显示 completed。无来源、非法引用、调用失败分别保留原因。失败节点可保存失败步骤和可查的拒绝结果，不能将未验证答案写作成功消息或已验证记忆。

## 4. 领域写入与来源校验

在既有六类 `WriteAction` 内扩展领域写适配，不改变合成端口的精确字段约束。领域步骤明确 role、status、input、output 等受信字段；相应回执使用独立 schema 标识，历史 v1 由原适配器读取，不能跨运行时解释。

assistant 消息必须对应已验证的 finish 输出。逐项校验引用的索引、同案文档、实际页码、名称、原文片段及宿主生成跳转路径；非法/跨案/过期引用拒绝，不能只允许“任意非空列表”。法条通过当前精确语料和引用协议核验。来源检查只证明身份与引文一致，不证明法律适用或语义支持。

缺口、记忆和消息子动作键从固定 node/key 派生，稳定排序，不依赖随机 ID 或重试计数。`persist_memory=false` 不产生记忆；草稿保持待确认，证据业务审批不因框架审批而变化。一个节点多项效果须和该节点步骤回执一起原子提交，查询核对其完整性。

保留 500 页/200 万字符的输入上限。领域 finish 结果含完整页面包，写入序列化上限需覆盖既有检索包的 UTF-8 字节数并设硬界限；不能以截断正文或引用获得通过。wire 仍有明确报文上限，宿主不把完整源库发给框架。

## 5. 模型与用量边界

D04 单独设计实际 LLM 受控模型端口以及 embedding/reranker 的受控检索调用。真实模型请求使用宿主有效配置，限定已获准的本机服务；核验实际权重/config/revision，未知项如实记录。私有快照外的旧正式入口旁路继续在 E01 留账。

模型的派发记录、固定输入、预算预留、响应和实际用量必须持久化。响应无 usage 或派发后失联时保持未知用量/待对账，不能映射为 SDK 默认的零 token，也不能凭缺响应盲重发。持久模型结果与节点输入绑定，业务写回执不代替模型调用结果/费用证明。

先用离线替身覆盖模型失败、额度、超时、非法输出与缺 usage，再按本次授权核查已有本机服务。缺少可核验身份或服务时记录实际限制，不安装/下载另一模型顶替，也不扩大到外发或付费调用。

## 6. 兼容、故障与验收

框架状态仍是唯一执行事实来源。新增领域运行时必须从旧启动恢复 SQL 中排除，避免宿主重启先把其 run 标成“可安全重试”；unknown 保留准入责任。旧合成图及其测试、旧公共协议/历史请求语义均保留。

按计划 D-A01–D-A11，覆盖领域节点结果生成前后、宿主 SQL/回执、SDK journal/checkpoint、完成投影六类持久窗口，以及实际模型另设的派发/响应/用量窗口。SIGKILL 使用真实进程组，新宿主与新框架进程恢复；重复受理/恢复/投影不得增加业务效果。

D01 是设计交付，不能作为 D02–D06 已实现或通过的证明。后续根据实际接口差异补充设计决策及适用例外；实现、检查和范围结论以[实施记录](domain-integration-execution-20261023.md)为准。
