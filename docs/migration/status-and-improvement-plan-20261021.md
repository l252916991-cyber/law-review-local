## 3. 问题清单与优先级

P0 表示下一阶段接入或交付的前置条件，P1 表示对应功能启用前必须完成，P2 表示随阶段收口完成；这是实施顺序，不代表线上漏洞严重性评级。

| 编号 | 级别与问题 | 证据及影响范围 |
| --- | --- | --- |
| I-01 | **P0：重复请求缺少原请求绑定校验** | 已隔离复现。`_replay()` 只按 `request_id` 获取关联；同键换案件返回旧运行 ID/状态，换问题或运行时也静默复用。没有返回答案；`inspect()` 会独立拒绝跨案访问；尚未暴露为实际 HTTP 路径 |
| I-02 | **P0：可信身份契约未落实** | 静态审查。请求中的 `actor` 没有与当前认证主体比对，`user_name` 直接进入协调器；原 API 的身份归一化规则尚未迁入适配层。风险为作者归属与契约不一致，未证明可伪造管理员权限 |
| I-03 | **P1：事件去重约定与可变节点记录冲突** | 静态审查。`inspect()` 按步骤行序号投影事件，LangGraph 恢复会原地更新步骤；按 `(run_id, seq)` 去重的消费者可能漏掉失败→完成更新。尚未执行消费者端故障复现 |
| I-04 | **P0：离线基线缺少冻结实验配置** | 本轮 3 项测试失败。需要从可信来源恢复文件及其身份，不能编造数据或修改指纹断言让测试通过 |
| I-05 | **P0（交付前）：源码包不能重建登记的框架绑定** | 已核对允许清单。wheel 与 `vendor/FRAMEWORK_BINDING.json` 均不在发布包和源码身份清单内；wheel 本体摘要与绑定记录相符。现有未接线产品不受该依赖影响，但迁移交付不可据此复现 |
| I-06 | **P0（正式绑定前）：发行身份冲突及框架审计未通过** | 律所 wheel 为 `8275baba…`，电商为 `58579893…`，都叫 0.5.0；候选 `qualified=false`。必须区分发行版本并完成适用门禁 |
| I-07 | **P1：真实运行入口和业务状态尚未统一** | 源码确认。API 仍直接使用旧协调器；后台仍修补私有 `_start_run` 获取运行编号。现有恢复路径尚未形成原 job、run、会话结果的一致收口；本轮未进行 HTTP 复现 |
| I-08 | **P1：只读迁移不能只关闭记忆保存** | 源码确认。`persist_memory=False` 不会禁止运行、步骤、疏漏及审计等全部写入；M2 对照必须隔离源数据库与副作用出口 |
| I-09 | **P1：自定义编排写入及恢复缺失** | 框架明确限制，属于已知待建设能力。复用 R1/R2 实现，不在律所再造一套旁路恢复机制 |

## 4. 分阶段改进工作包

### A. 补强 M1：先稳定接入边界

**A1 请求身份与幂等绑定（I-01，律所集成负责）**

- 先统一可信上下文字段和归属规则，再为请求保存版本化规范摘要：案件/作用域、认证主体、运行时、问题及影响执行的参数；明确 request_id 命名空间。
- 完全相同的重试才能返回旧关联；同键不同请求明确拒绝，不执行、不写入结果；返回旧运行前重新核验该运行的实际案件授权。
- 旧记录没有摘要时采用明确的兼容或对账状态，不能视为任意新请求的成功重放；并发申领和崩溃窗口继续防止重复副作用。
- **验收**：跨案件、换主体、换问题、换运行时、换关键参数、撤权、并发和崩溃用例；合法重试仅一个业务运行，冲突不泄露旧关联详情。

**A2 可信身份与数据库作用域（I-02，与 A1 共用字段设计）**

- 宿主认证层构建执行上下文；保留原有作者归一化行为，明确客户端展示姓名与可信操作者的区别。
- 当前单租户实现显式拒绝不支持的 tenant，避免接受看似有效而实际未隔离的租户字段。
- 后台执行与恢复保留现有主体/数据库作用域保护，并在执行和读取时复核实时权限。
- **验收**：伪造姓名被拒绝或归一化；记忆作者和审计主体正确；延迟任务、恢复、撤权及错误租户不越界。不能仅测试 dataclass 字段非空。

**A3 状态与事件语义（I-03，可与 A1/A2 的实现并行）**

- 推荐旧运行时明确提供“快照 + 修订号”，消费者按修订更新；框架事件流采用持久化追加事件。适配层明确两种语义，不能继续把可变步骤序号宣称为不可变事件身份。
- 若选择统一追加事件方案，则先完成持久事件表和兼容投影；单独提升协议版本号不能解决漏更新。
- **验收**：失败→首次读取→恢复→再次读取→进程重启后重取，消费者最终显示完成且无重复业务副作用；重复及乱序读取具有明确规则。

交付物：补强后的契约、必要 schema 迁移、回归测试、`m1-contracts.md` 与台账更新。现有同步 API 与新接口之间先补兼容测试，再启用接线。

### B. 修复基线与发行交付：与 A 并行

**B1 冻结配置与验证（I-04，验证维护负责）**：从原仓库或可信备份恢复实验配置，核对来源、指纹和适用数据；恢复后重跑三个失败用例及完整离线范围。找不到可信原件时，保留既有失败，单独登记旧实验不可复现；如需新实验，制定新版本协议和身份，不能冒充原冻结配置。检查应交付的非敏感测试固定输入是否明确纳入发布允许清单。

**B2 框架发行与审计（I-06，框架维护负责，复用 R7/R8）**：处理保存报告中的依赖审计失败并重跑适用门禁；为内容改变的发行物使用不同版本号，冻结源码、锁、wheel 和协议摘要。业务质量资格独立保留。隔离开发可继续，未通过的候选不能标成正式验收完成。

**B3 可重建交付（I-05，框架与宿主共同负责）**：建立部署依赖清单。可以将经审查的绑定记录及精确 wheel 纳入安全允许清单，也可采用可获取的不可变发行物、摘要校验和明确安装步骤。只选择一种可验证的正式交付路径；不能无差别打包 `vendor/` 或私人数据。源码清单与部署清单分别声明覆盖范围。

**验收**：从实际源码发布包解压后，在隔离环境重建框架绑定、校验摘要并运行契约冒烟；不依赖开发机绝对路径和未打包的本地文件。执行适用 Python/Node 矩阵；为缺失语料及可选依赖的测试分别给出明确结论。

### C. M2：接入律所真实只读链路

依赖 A 的接入边界、B 的明确发行身份与只读范围门禁；不等待完整 R1/R2 写入恢复实现。由律所集成人员负责，框架提供 SDK/材料契约支持。

- 用原专家、原混合检索和受控法条端口替换词匹配示例；保持现有业务路由及模型选择，避免同时更换模型导致无法归因。
- 使用隔离快照或只读源连接，运行日志与允许的试验输出写入独立位置；逐项阻断对源宿主的记忆、疏漏、运行、审计等写入。
- 贯通实时授权、撤权、超时、缺页、空检索、材料上限、来源身份及严格引文失败路径；超限显式处理，不静默截断。
- **验收**：源业务数据零变更；新旧链路结果、引用及失败差异可追溯。工程对照先用合成材料；真实案件对照使用已授权范围，记录数据身份和领域评审结论。

### D. M3/M4：恢复能力与产品接入

框架侧复用 R1/R2 实现共享工具执行、审批资格、journal、预算和自定义节点恢复；律所侧接同步 API、后台任务、轨迹、恢复、会话、桌面/移动页面，移除对私有 `_start_run` 的修补。产品接入设计和兼容测试可以提前准备，正式启用依赖 A、C 和适用的框架恢复验收。

**验收**：一次请求稳定关联 request/job/run；恢复后运行状态、任务状态和会话结果一致。超时、重启、并发、撤权、部分工具成功和结果保存失败均有验证；不确定副作用进入对账，不盲目重试或切旧引擎重复执行。HTTP/UI 验证需确认运行进程加载的是被测代码。

### E. M5/M6/M7：验收、切换与推广

- **M5**：冻结源码、发行物、数据与评分版本；完整工程验证、干净安装、领域评审、成本/时延和故障演练分别给出结论。引文文字匹配通过不能代替法律适用及证据支持审查。
- **M6**：通过后再按案件或主体小范围启用，观察后调整新任务默认。旧运行由原引擎完成或明确终止；回滚新任务路由时保留已发生的新业务数据，不以旧数据库覆盖。符合退出条件后删除重复执行路径。
- **M7**：电商真实宿主验证同一受支持框架发行线与共同契约；逐个登记其他实际项目的接入、业务验收和旧路径处置。新项目模板从这两次实际集成提炼。

**最终完成定义**：登记范围内每个实际项目都有可重建绑定、通过的适用契约、实际业务验收和旧运行时处置记录；框架核心不含法律或电商专属分支。不是“两个 demo 能运行”或“所有项目复制相同目录”。
