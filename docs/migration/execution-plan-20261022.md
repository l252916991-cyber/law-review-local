# ForgeHarness 统一框架替换执行计划书

编制日期：2026-10-22（北京时间）｜版本：1.0｜状态：待按任务逐项实施。

本执行书承接[总体替换路线](../architecture/forgeharness-migration-plan-20261021.md)，以[迁移台账](ledger.md)、[M1 契约](m1-contracts.md)和[M2 工程记录](m2-engineering-20261022.md)为当前依据。本文明确剩余工作、执行顺序和验收条件；编制本文不表示启动真实模型调用、生产切换或完成任何待办任务。

## 1. 目标、范围与完成定义

将 ForgeHarness 建设为各实际项目共用的 Agent 运行底座，统一模型和工具调用治理、预算、审批执行、执行记录、恢复、版本和交付。各项目继续拥有领域规则、身份权限、业务数据库与产品界面。

当前明确纳入 LexVault「本地律所」、ForgeCommerce「电商agent」及其所需的 ForgeHarness 公共能力。台账中的 ERP、AI 视频、deepseek-harness 等候选目录，在 E01 中逐项确认迁入或排除；登记排除原因，不把参考源码、内容目录和开发工具自动算成业务迁移对象。新增实际项目另列任务和估算。

“全部 AI 入口”包括普通问答、Agent 阅卷、后台任务、分析、工具调用、模型化检索、向量索引与评测入口。各入口登记适用治理方式；确定性函数、单 Agent、固定 DAG、多 Agent 均可接入。普通 CRUD、导入、文件服务和业务审批继续由宿主实现，相关模型调用按登记的受控端口执行。

完成替换须同时满足：

- 纳入范围的每个项目、每个 AI 入口均有归属、框架版本、能力声明和验收记录。
- 新业务任务默认使用 ForgeHarness；模型、工具、后台执行和恢复没有未登记的治理旁路。
- 框架拥有执行状态，宿主业务表通过幂等投影与回执反映状态；业务数据继续由宿主授权写入。
- 各项目通过自身工程、业务与实际产品流程验收；历史可读，旧任务有明确归宿。
- 旧在线调度在观察和回退窗口结束后退役；临时例外有责任人、用途及到期日。
- 后续项目使用共同接入模板和受支持发行线，禁止长期复制或私改框架核心形成分叉。

本轮不包含更换法律判断标准、全量业务搬库、重做 UI、公网多租户平台、真实支付退款或新增店铺渠道。这些需求出现时另立任务，不隐含进入当前估算。

旧 RunEvent v2 是内容修订号标记的快照投影，hash 不具时间顺序。新持久事件采用明确的追加序号、游标与去重规则；语义变化按契约升版，并保留历史投影适配。页面须防止并发轮询的旧响应覆盖新响应。

框架执行审批与律师对证据的业务审批分别建模，不给既有内部结果保存无条件增加人工确认。框架与宿主之间不假设跨库原子提交，以持久回执、投影重试和对账处理故障。

## 6. 故障与验收矩阵

### 6.1 必须注入的故障窗口

| 编号 | 注入位置/条件 | 预期行为 |
| --- | --- | --- |
| F01 | 相同 request_id 重复、并发提交或更换参数/主体 | 相同有效请求只受理一次；不同请求冲突拒绝，不泄露旧关联 |
| F02 | 业务 run 已提交，关联回调丢失 | 保留请求声明，进入对账；不能按“没收到回调”重跑 |
| F03 | 工具准入后、执行前进程退出 | 根据持久调用状态判断能否执行，不凭内存猜测 |
| F04 | 业务写入完成、回执送达前退出 | 宿主查询回执；幂等重试不重复产生效果 |
| F05 | 工具返回后、节点 checkpoint 落盘前退出 | 查证持久调用结果与节点输入身份，复用完成结果或进入待对账 |
| F06 | 待审批时重启、重复批准、参数/资源版本变化 | 重建精确待审批动作；审批不可跨动作复用；变化后重新校验或拒绝 |
| F07 | 并行节点争用预算、部分失败、重复 join | 累计预算不丢失、不超额分配；join 与终态持久且幂等 |
| F08 | 执行中撤权、删除案件、资料或法条版本变化 | 停止后续访问/写入；历史查询与恢复重新授权；不返回失效成功 |
| F09 | 队列满、取消、worker 重启、完成事件重复/乱序 | job/run/会话收敛；额度只释放一次；无重复消息或永久伪运行态 |
| F10 | 协议不匹配、旧 checkpoint、sidecar 断连、总超时 | 明确拒绝、终止或待对账；无自动跨运行时重放；资源清理可验证 |

E10 使用契约替身验证适用的框架层故障语义，不依赖尚未完成的真实宿主产品。F02/F04/F09 等宿主回调、写入回执与 job/会话场景随 E12–E15 实现接入；E16 对最终候选执行全部适用的端到端 F01–F10。增加新副作用类型时补相应故障窗口。

### 6.2 放行口径

| 维度 | 门槛 |
| --- | --- |
| 权限与副作用 | 适用验收集中未授权读取/写入、未批准或重复副作用、虚假完成、来源身份错误均为零；任一发生即阻断切换 |
| 确定性领域行为 | 规范化结果契约一致；明确离线与失败降级；不得遗漏现有业务能力 |
| 检索与引用 | 来源身份、原页/法条版本、精确引文可定位；专业评审另外判断语义支持，不能以字符串匹配替代 |
| 模型与业务 | 开发集与独立终评集分开；终评至少 16 个独立业务题并补异常/规模场景；关键题无新增严重错误；必要时每题重复 3 次，重复不增加独立样本数 |
| 性能与用量 | 提案：相同模型/资料/并发下 p95 不超过旧基线 1.20 倍，实际 token 不超过 1.10 倍；绝对超时、金额/用量上限由 E03 冻结。样本不足不宣称稳定 p95，未知用量不填零 |
| 工程 | 以各项目当前 CI 与 AGENTS 为准，不能跳钩子、删失败测试或降低覆盖率；本机、托管 CI、干净安装和模型评测分别出结论 |
| 生命周期 | 案件撤权/归档/删除/保留规则覆盖框架 trace、checkpoint、报告与导出；必要历史读取按授权保留 |
| 跨应用 | 两个真实宿主使用公共契约；全部登记项目逐项验收；安装同名包或运行样例不算统一完成 |

上述题数和试点次数是最低试点要求，不构成生产泛化或统计充分性的证明。门槛尚待冻结的项目保持未验收；失败不能被其他题平均分抵消。

## 7. 验证操作与证据保存

### 7.1 每个工作包的执行闭环

1. 核对适用 AGENTS、当前分支/差异、任务依赖和既有改动，记录本次精确文件范围。
2. 保存实现前的源码/依赖身份；无 Git 时使用现有清单工具和必要的修改前副本。
3. 完成单一主题实现及有实际断言价值的测试，更新对应契约与文档。
4. 先运行受影响检查；跨模块、数据结构、依赖或 CI 变更按现有规定运行完整离线检查。
5. 审查最终差异和发布清单；验证后又改代码则重跑受影响检查。
6. 记录结果和遗留问题。Git 可用时仅暂存本任务明确路径，检查暂存差异后原子提交；Git 未恢复时保存摘要与差异并说明未提交原因。
7. 只有交付物及退出条件都有对应证据，才将任务改为“已完成”。

### 7.2 律所离线检查参考

### 7.3 证据要求

每次执行使用新目录，例如 `output/migration/<任务编号>-<日期>-<唯一编号>/`，不覆盖旧成功或失败报告。框架证据留在框架项目，台账记录交叉引用。含真实材料的报告保存于获准的私有位置，不纳入源码发行物。

每份任务完成记录至少包含：任务编号、状态、负责人、源码/依赖/发行物摘要、Git 提交或无 Git 原因、数据快照、模型配置、执行命令、环境、开始结束时间、通过/失败/跳过、原始证据位置、遗留问题、验收人及下一依赖。模型记录不含密钥。

工程检查、模型评测、专业评审、实际 HTTP/UI、生产试点分别给结论。报告只绑定实际被检查的候选；代码或依赖变化后旧报告保留为历史，不覆盖后继续沿用结论。

## 8. 切换、回退与退役操作

### 8.1 切换前检查

- G2/G3/G4/G5 均通过，Git/发行来源和当前 schema 的回退兼容性有记录。
- 按现有停写备份流程保存业务数据及关联框架状态，已在隔离目录成功恢复。
- 试点主体、材料范围、运行时固定规则、模型预算、运维负责人及观察门槛已落实。
- queued/running/待审批/待对账的旧运行均已盘点，历史读取已验证。

### 8.2 回退触发与执行

跨范围访问、重复或未批准写入、来源身份错误、结果丢失、错误恢复、持续超过冻结的资源限额触发暂停。执行顺序：

1. 关闭新框架的新任务准入，保留诊断证据和影响范围。
2. 盘点 queued/running/待审批/副作用未知任务，停止或排空相应 worker。
3. 对照框架调用日志、节点状态和宿主回执完成对账。
4. 只有确定未执行的新请求可以进入旧运行时；同一未决请求禁止跨运行时盲重放。
5. 启用已演练、能读取当前 schema 的兼容版本，验证 API、页面和历史读取。
6. 保留切换后合法业务数据；如确需数据恢复，先形成前向数据保全和对账方案，再按适用授权实施。

现有旧代码可能因 schema 防降级检查拒绝新库；“代码可以回退”不代表“数据库可以直接降级”。禁止直接恢复旧备份覆盖当前业务库。当前 sidecar 是受信代码的进程与环境分离，不是用于不受信代码的操作系统沙箱。

### 8.3 旧路径退役条件

旧 LangGraph checkpoint 不直接转成 ForgeHarness checkpoint。旧任务分别在原版本完成、经授权终止并创建新 run，或归档为不可恢复历史。无未决旧任务、历史可读、替代恢复通过、观察和回退窗口结束后，才删除旧在线调度及专属依赖。

历史结果、审计、受保留政策约束的 checkpoint 不随代码退役自动删除。必要的历史读取适配可保留，但不得继续隐式受理新业务任务。例外运行时必须登记退出日期。

## 9. 首轮实施顺序与协作方式

后续开始执行时，第一批按以下顺序交付，每项独立验证：

1. E01–E03：补齐入口/项目清单、基线与验收参数；未落实的外部条件明确挂到相应任务，不阻塞无依赖工程。
2. E04：完整只读端口及公共控制接口的适用能力，保持现有 M2 合成对照回归。
3. E08：框架共享工具执行器，先完成既有路径复用与共同契约，再连接 kernel。
4. E06 与 E09：资料身份/规模工作和持久恢复协议可并行，冻结接口后合入。
5. E05/E07 与 E10/E11：分别完成受控模型与对照、恢复故障与发行资格；按依赖取得 G2/G3 后进入完整产品接线。

协作可分为框架、宿主、验证三条工作线，由集成人员协调接口和文件归属。并行前约定协议及修改范围，避免同时编辑同一关键模块；共享契约变化先通知依赖工作线。不得把相同框架能力在律所与电商各实现一次，也不得按代理数量直接折算工期。

存在 Git 基线后，按主题创建或沿用 `codex/<主题>` 分支，每个独立完整改进验证后原子提交。无 Git 时继续保存可复现清单及精确差异；初始化基线仍需要明确授权，不能因本执行书自动收录全部已有文件。
