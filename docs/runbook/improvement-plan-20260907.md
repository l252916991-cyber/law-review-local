# LexVault 深化改进计划书：领域子智能体、模板化结案、多人部署

计划日期：2026-09-07（Asia/Shanghai）
计划对象：`law-review-local` 当前 `main`（含批次 1/2 全部治理提交）工作树
主要读者：项目负责人、后端/测试、运维、拟接入试点的律师
状态：改进规划；本文件只定义目标、设计与验收标准，不表示任何能力已实施或验证

## 0. 背景与定位

对标一个商用私有化阅卷方案（面向律所的定制部署，含多卡服务器、多智能体分工、模板化结案与局域网多人使用）后，识别出三个本项目的差距点。本计划将其整理为可执行工作包，并纳入既有路线图体系（`enterprise-improvement-report.md` 的 E01–E30、G0–G3 阶段），**不另立互相冲突的路线图**：

| 本计划工作包 | 对应既有编号 | 阶段定位 |
|---|---|---|
| E31 金融犯罪显式子智能体分工 | 深化 E07（答案质量契约）、服务 E13（对抗测试） | G1→G2 |
| E32 预设模板结案打包 | 细化 E08 的"导出"半边（E08 并发控制半边另行排期） | G1 |
| E33 面向律所的多人部署形态 | 落地 E22（安装升级）与 G2 阶段门槛；**不是** E30 多组织 | G2 |

优先级建议：**E32（快赢）→ E33（解锁真实用户）与 E31 P1–P2 并行 → E31 P3（资金链路，最重）**。理由：E32 一至两个工作日可交付且立即改善交付物；E33 让系统进入真实多人使用闭环；E31 的深度质量提升放在前两者稳定之后。

统一边界（适用于全部三个工作包）：
- 不做模型微调，不引入付费云服务；推理仍走本地 oMLX（8-bit Qwythos 9B + 既有 embedding/重排）。
- 不做 E30 多组织/多租户；E33 的边界是**单组织、局域网、数十人量级**。
- 每个工作包交付时区分：已实现（源码确认）、离线验证（测试/基准）、待部署验收（真实环境）、需人工裁决四类证据口径。
- 证据链纪律沿用现状：凡 AI 结论必须带引用，凡导出必带哈希清单，凡变更必留审计。

## 1. E31：金融犯罪显式子智能体分工

### 1.1 现状与差距

现有能力（均为已实现、离线验证）：
- 原生 + LangGraph 双 Agent 运行时（`app/agents.py`、`app/langgraph_agents.py`），失败可从 checkpoint 恢复；critic 结构校验（`validate_review_answer`）强制引用格式。
- 证据图谱（`evidence` + `evidence_relations`，关系类型含相互印证/相互矛盾/资金链路）与疏漏检测（`gap_detections` 表）。
- 口供语义映射（`expand_semantics`）、三路检索路由（`detect_route`）、人工校准与标注（`evidence_annotations`）。
- statutory RAG 基建成熟（`app/legal_corpus.py` v10–v19 语料、版本歧义拒绝、哈希校验），但目前主要服务基准链路（1-1=81.61%、3-1=85.52%、3-3=54.67%），**产品侧问答尚未接入法条检索**。

差距：分析流程是"单一问答 + 路由"，没有面向金融犯罪案卷的**显式子智能体分工**；资金流水虽是证据类别（银行流水/审计报告），但只有文本页级存储，没有结构化的资金链路分析。

### 1.2 目标设计

子智能体 = 结构化提示模板 + 限定检索范围 + 输出结构校验 + 独立溯源记录，全部跑在现有单一本地模型上（不新增模型，provenance_json 照常记录）。编排由 LangGraph 图承接，可并行的子智能体并行，可恢复。

| 子智能体 | 输入范围 | 输出（落库位置） | 复用现状 |
|---|---|---|---|
| 案卷分析协调者 | 案件全目录 | 分析计划、子智能体调度 | LangGraph coordinator 改造 |
| 基本事实判断 | 全部文书页 | 结构化事实条目 + 引用 | 现有问答/`auto_analyze_case` 提炼 |
| 证据清单生成 | 文书 + 证据表 | 证据清单（含待补充项） | `auto_analyze_case` 候选证据 |
| 证据矛盾与错误判断 | 证据对 | `evidence_relations`（相互矛盾）+ `gap_detections` | 疏漏检测升级 |
| 证据与法条矛盾判断 | 证据 + 法条语料检索 | 矛盾条目（引法条版本+条号） | **产品侧接入 legal_corpus**（新增） |
| 资金链路分析 | 流水证据 | 结构化交易表 + 汇总 + 资金链路关系 | 全新（见 1.3 P3） |
| 人工意见及补充 | `evidence_annotations` + 校准记录 | 分析结论中显式引用人工意见 | 标注表接回分析回路（新增） |

硬性契约（沿用并强化 E07）：
- 每个子智能体输出必须过 `validate_review_answer` 级结构校验；关键事实/矛盾/金额必须带 `[资料N]` 引用，无法核验处标注"待核验"，不得臆断。
- 现状中 `semantic_entailment_checked=False`、`amount_calculations_checked=False` 两个诚实标记保持——子智能体输出仍一律标注"AI 草稿，待律师复核"，不宣称语义正确性或法律正确性。
- 卷宗文本是不可信输入（E13）：子智能体提示词中卷宗内容不得改变工具授权与检索范围；补对抗夹具测试（提示注入不改变子智能体行为）。

### 1.3 实施步骤

- **P1（S–M）子智能体骨架**：定义统一的子智能体接口（输入上下文范围、输出 schema、校验器）；把"基本事实判断/证据清单生成"先从现有能力改造为显式子智能体，编排入图；run 轨迹页面按子智能体分节展示。验证：现有 390 项离线测试不回归；新增子智能体结构/失败恢复测试。
- **P2（M）矛盾与法条子智能体**：证据矛盾子智能体升级 `gap_detections`；法条矛盾子智能体产品侧接入 `legal_corpus`（复用基准侧 statutory 检索实现，版本歧义直接输出"待核验"）。验证：合成案卷上矛盾检出的精确/召回抽样报告；法条引用必须通过版本/条号核验的单元测试。
- **P3（L）资金链路子智能体**：新增 `bank_transactions` 结构化表（来源流水文件、账户、方向、金额、时间、对手方、原始页引用）；首期提供显式 CSV 流水导入，XLS/XLSX 需后续明确依赖后开放（PDF 扫描件仍走页文本，不承诺表格还原）；汇总（按账户/对手方/时间段）与 `资金链路` 图谱 API 已实现。验证：5 个合成流水解析/服务测试 + 89 个聚焦测试通过，金额汇总逐笔复算，导出清单包含流水表哈希。
- **P4（S）人工意见子智能体**：律师标注与校准记录进入分析输入，输出中显式区分"AI 判断"与"已引用人工意见"。验证：人工意见被篡改/删除时分析引用失效的测试。

### 1.4 验收标准与证据

- 每个子智能体：正常/异常/对抗三类离线测试通过；输出 100% 带引用或显式"待核验"。
- 端到端：演示案卷（合成）从上传到结构化分析产出一键完成，结果可逐条溯源到页。
- 质量测量（E24 纪律）：建立金融犯罪小型验收集（合成起底，≥20 题/子智能体，参考答案不进推理），分项报告；真实卷宗正确率与效率的结论必须由律师标注产生，属外部验收。
- 红线：不宣称"证据矛盾已由 AI 判定"，表述统一为"AI 提示的矛盾点，待律师复核"。

## 2. E32：预设模板结案打包

### 2.1 现状与差距

`build_export`（`app/services.py`）输出固定内容：案件摘要、内容级/证据目录 CSV（公式注入中和）、问答记录、原始卷宗、带 sha256 的清单.json。差距：内容与顺序固定，不能按律所/案件类型预设模板；AI 阅卷总结/质证记录等结构化成果不进包；缺少"律师一次性提交、系统按模板拼接"的结案动作。

### 2.2 目标设计

- **模板模型**：结案包 = 有序区块列表。区块类型枚举（首期六种）：静态 Markdown、案件摘要、目录 CSV、证据表（可按状态过滤，如仅"已确认"）、问答/质证记录、附件（原始卷宗选集）。模板为 JSON，存 `export_templates` 表（含版本号、创建人、审计），预置两个内置模板：刑事阅卷结案包、质证材料包。
- **渲染规则**：缺失字段渲染为显式占位符（如"[待补充：申辩意见]"），不静默跳过、不崩溃；CSV 一律过 `csv_safe_cell`；清单.json 扩展记录模板 ID/版本与渲染器版本，全包哈希链保持。
- **结案动作**：案件页新增"按模板打包结案"入口 → 校验必选区块数据齐全（缺失列出清单）→ 生成 → 审计记录（谁、何时、哪个模板、包哈希）。
- **权限**：模板管理归 `manage`；打包动作归 `export`，与现行矩阵一致。

### 2.3 实施步骤

1.（S）`export_templates` 表迁移 + 模板 CRUD API + 内置模板种子；验证：迁移有序性、权限矩阵覆盖。
2.（S）`build_export` 重构为区块渲染器，保持现有默认输出逐字节兼容（现有测试不回归）。
3.（S）结案动作端点 + 必选区块校验 + 审计；前端案件页入口。
4.（S）模板版本变更不影响历史包可解释性（清单里留模板快照）的测试。

### 2.4 验收标准与证据

- 离线：模板渲染（齐全/缺字段/空案件三类）测试、CSV 注入安全不回归、清单哈希可复算、越权（非 manage 建模板、非 export 打包）测试。
- 真实验收：律师用真实模板完成一次结案打包并确认内容可用（外部验收，人工）。
- 红线：草稿与已确认内容在包内必须显式区分（沿用 E08 的"草稿导出明确标识"）。

## 3. E33：面向律所的多人部署形态（G2 落地）

### 3.1 现状与差距

已具备（多数为批次 1/2 交付、离线验证）：token 多主体 + 案件授权 + 权限矩阵；服务端会话（8h 过期、注销吊销）；Web 单进程所有权锁；arq worker 隔离；Redis 探测 + outbox 重派；`docker-compose.yml`（web/worker/redis）已写但**镜像从未构建**；快照/恢复工具与演练手册；请求关联 ID 与结构化日志；ready/liveness 分离。

差距（按重要性）：
1. **会话不持久**：`_sessions` 为进程内存字典，Web 重启全会话失效（现有文档已如实标注）——多人形态下不可接受。
2. **部署未经验收**：Docker 镜像未构建、干净机器安装未演练、TLS 反向代理边界（HSTS、转发头、Host 校验）未实测。
3. **升级路径未演练**：迁移 v1→v5 有测试，但"真实旧库 + 备份先行 + 回滚"未在部署形态下走过。
4. 容量无实测：并发读 + 少量写的 SQLite WAL 在律所量级（≤50 并发读、≤5 并发模型请求）是否够用，需要数据。

### 3.2 目标设计

- **拓扑**：律所内网一台服务器（或高配 Mac Studio），`docker compose` 跑 web + worker + redis；前置 Caddy/Nginx 做 TLS + HSTS，强制 `LAW_REVIEW_AUTH_MODE=token`；模型服务（oMLX）独立进程/机器，作为显式外部依赖；数据卷每日快照 + 异地副本。
- **会话持久化**：`_sessions`/`_oidc_sessions` 迁移到 SQLite 表（键仍为哈希、TTL 语义不变、注销/轮换语义不变），启动时清理过期行；保持"每请求重读当前授权映射"的既有语义。容量上限与清理策略随迁。
- **容量护栏**：模型请求并发由既有 indexing/queue 信号量控制并配置化；文档化"1–3 路并发模型请求"的建议硬件规格（与视频方案的差异：单机 96G 级 GPU 可选，Mac 适配栈为默认参考）。
- **升级与回滚**：发布前强制快照；迁移失败回滚流程写入 runbook 并演练一次。

### 3.3 实施步骤

1.（S）会话持久化迁移 + 重启存活/过期清理/吊销语义回归测试。
2.（M）Dockerfile 实际构建 + 干净机器 compose 起站 + TLS 代理联调（Host 校验、转发头拒绝策略在代理后实测）；产出《律所部署手册》（含硬件规格建议、首次配置清单）。
3.（M）升级演练：v4→v5 真实库备份→升级→回滚走一遍并存证；恢复演练按 runbook E18 章节执行一次（含 Redis 丢库 outbox 重派）。
4.（M）双人并发端到端验收：两个主体同时登录，各操作各自授权案件，会话/审计/隔离断言；轻负载冒烟（p95 延迟与错误率报告，**不承诺 SLA**）。

### 3.4 验收标准与证据

- 部署验收矩阵（逐项留证）：干净机器安装（非开发者按手册可完成）、重启后会话存活、备份→恢复→业务可用、代理边界注入测试（伪造转发头/Host 被拒）、双用户隔离、升级回滚。
- 红线：在部署验收完成前，README/报告不得表述"支持律所多人生产使用"，只能表述"具备 G2 部署能力待验收"；不宣称安全认证、等保或 SLA。

## 4. 里程碑与排序建议

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| M1（约 1 周） | E32 全部 + E33 步骤 1 | 模板打包离线验收全过；会话持久化合入 |
| M2（约 1–2 周） | E33 步骤 2–4 + E31 P1 | 部署验收矩阵全过（进入 G2 试点）；子智能体骨架合入 |
| M3（按试点反馈） | E31 P2–P4 | 子智能体验收集分项报告 + 律师复核结论 |

里程碑时间为估算而非承诺；每阶段出口以验证证据为准，不以日历为准。

## 5. 统一验证与交付规则

- 沿用仓库既有纪律：每主题独立原子提交；Python 变更跑受影响测试 + `uv run --locked ruff check app tests scripts`；跨模块变更跑完整离线套件（当前 390 passed / 86.73% 覆盖为基线，只升不降）；工程脚本跑 mypy；前端跑 `node --check` 与页面验证。
- 涉及部署的验收（Docker、TLS、双用户、恢复演练）必须在目标硬件/干净环境执行并逐项留证；本机部分通过不算部署验收通过。
- 每个工作包关闭时更新 `enterprise-improvement-report.md` 对应条目状态与本计划的出口记录。

## 6. 需要组织决策的事项（代码无法自答）

1. 试点律所/律师人选与真实卷宗使用授权（E33 试点与 E31 验收集的前提）。
2. 服务器采购与放置（E33 拓扑二选一：律所内网服务器 vs 高配 Mac 托管）及谁负责日常快照检查。
3. 结案包模板的法定内容清单（E32 内置模板的字段需要执业律师确认，工程侧只保证渲染与防注入）。
4. E31 质量口径：律师标注验收集的规模与双人标注安排（E24 协议）。
