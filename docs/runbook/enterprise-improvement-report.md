## 1. 总体判断

LexVault 已具备本地法律卷宗工作台的主要技术基础：多格式导入、页级存储、混合检索、证据管理、双 Agent 运行时、运行轨迹、失败恢复、最小案件授权、离线工程测试及备份工具。建议保留这些基础，通过可验证的业务与运维改进逐步进入企业场景。

当前企业化工作的重点有四项：

1. 建立可追溯的证据链：原件、提取结果、引用位置、人工修订和派生结论绑定明确版本。
2. 建立可信的审阅闭环：区分模型草稿、结构校验通过、律师确认和已失效结论；材料变更后及时更新相关结果。
3. 建立可运营的服务：权限、数据保护、迁移、恢复、容量、监控、发布及故障处置都有实际验收证据。
4. 建立独立的业务评测：衡量律师处理真实卷宗的完整性、正确性和工作效率，分别报告模型题库、检索和应用结果。

目前可以支持继续开发与受控验证；是否允许真实敏感卷宗试点、多人使用或正式交付，应分别通过本报告规定的阶段门槛。没有足够证据给出“企业级已达标”或同类项目排名。

依赖哈希提升安装完整性，但不证明组件没有漏洞或满足所有使用条件；供应链控制还需关注来源、更新、漏洞和构建产物。参考 [pip 安装安全说明](https://pip.pypa.io/en/stable/topics/secure-installs/)。

## 5. 关键设计契约

### 5.1 证据及派生结果版本

建议建立下列关联字段，具体表结构由 E16 的迁移设计确定：

| 对象 | 最小追踪信息 |
|---|---|
| 原件版本 | case_id、document_id、source_version、原件哈希、来源、接收时间 |
| 提取结果 | 原件版本、解析器/模型版本、参数、page/paragraph/cell/bbox、提取文本哈希、完整性状态 |
| 索引版本 | 提取版本、分段策略、embedding 身份与维度、索引构建状态 |
| 结论 | run_id、claim_id、引用片段及版本、实际推理配置、结构/语义/人工核验状态 |
| 审核记录 | 审核人、对象内容哈希、来源版本、决定、理由、时间 |
| 导出 | 导出人、案件版本、结论/证据清单、审核状态、文件哈希 |

原件哈希用于识别与完整性检查，不能单独证明材料真实性、取得过程或法律证明力。系统应保存来源和人工核验记录，保留这些概念的区别。

### 5.2 审核状态及失效

建议状态流为：`draft → pending_review → approved / rejected`；来源修订、撤回或关键配置导致重算时，受影响对象进入 `stale`，再重新生成或审核。

对每次批准保存被批准内容的确切版本；批准后不可原地改写内容继续沿用旧批准。审核撤销应形成新事件。恢复 checkpoint 后仍需重新确认当前权限、材料版本及审批有效性。是否利用 LangGraph interrupt 暂停，由产品流程决定；审核业务状态应可独立查询。

### 5.3 任务副作用与重试

所有可重试写操作明确幂等键及唯一约束；数据库提交成功但队列未确认、模型返回但结果未落库、取消与完成竞争均要测试。只对明确可重试的瞬时错误退避，并设置最大尝试次数与整次请求预算。永久错误、参数错误、鉴权失败不进行无意义重试。

后台执行时的身份快照不能永久替代当前授权。应定义撤销后任务继续、取消、结果可见性和导出策略，并在恢复与结果交付边界落实检查。

## 6. 验收数据与指标

### 6.1 数据集设计

建议 G1 首批建立 30 个独立案件包，其中 20 个用于开发，10 个作为冻结验收；每案至少设计 20 项人工核验任务，合计至少 600 项。它是启动规模，不能据此证明覆盖全部案由或所有极端情况。最终规模按试点案由、资料复杂度、错误置信区间和标注能力调整。

每个案件包至少登记材料来源、使用授权、原件清单、人物别名、时间、金额、事实、冲突、缺失材料以及可定位答案。样本覆盖：文本 PDF、扫描 PDF、同页混排、DOCX 表格、跨页表格、印章遮挡、低质量图片、重复件、版本修订、多主体、材料不足与恶意内容。

真实材料、公开材料和合成故障夹具分别标识。工程对抗及故障测试可以使用合成数据；律师效率和真实阅卷质量必须使用与目标场景相符的材料。由两名具备相应能力的标注人员独立核验关键项，记录一致率与分歧裁决。若已根据冻结验收结果持续调整策略，该集合转为开发材料，下一轮发布重新建立未参与选择的验收集。

### 6.2 指标口径与建议初始门槛

以下数值为本报告提出的起始验收目标，须在盲测前由试点负责人冻结；当前无达标声明。每项同时报告分子、分母、缺失值、失败、材料类型与样本量，必要时给出区间。

| 指标 | 定义 | 建议门槛 |
|---|---|---|
| 原件与定位一致性 | 可到正确原件版本及位置的引用 / 抽检引用 | 核心验收样本 100%；任何错案/错原件为阻断 |
| 关键内容提取召回 | 正确提取关键字段/表格单元 / 人工标注关键项 | ≥98%；金额、日期、否定等高风险错误单列，不能被均值掩盖 |
| 关键事实召回 | 正确覆盖的必要事实 / 标注必要事实 | ≥95%，并按材料类型分层 |
| 引用语义支持率 | 被引用证据确实支持的事实声明 / 带引用事实声明 | ≥98%；无引用关键声明另行计错 |
| 关键声明引用覆盖 | 有可核对来源的关键声明 / 全部关键声明 | 100%；不可支持内容必须显式标注不确定性 |
| 无依据确定性结论率 | 无依据却作确定表达的答案 / 被评答案 | 冻结高风险样本中为 0；不外推为线上零风险 |
| 材料不足处理 | 正确识别材料不足的题 / 应拒答或请求补充题 | ≥95%；同时报告对可回答问题的错误拒答率 |
| 金额/日期校验 | 自动确定的结果正确数 / 自动确定结果数 | 高风险工具验收样本 100%；同时披露自动覆盖率，低覆盖不能冒充完整能力 |
| 冲突/疏漏识别 | 人工确认的正确提示、应识别总项及误报 | 报 precision/recall；建议先以 recall≥90%、precision≥80% 为试点目标，分严重程度报告 |
| 修改后结果一致性 | 正确失效并更新的相关对象 / 应更新对象 | 100%，包含索引、记忆、引用与导出状态 |
| 授权边界 | 固定攻击矩阵中越权成功数 | 0；矩阵范围、身份、接口和负载须披露 |
| 律师效率 | 同等质量要求下的完成时间及返工量 | 建议中位时间减少≥20%，且关键漏检与错误不得增加 |

效率实验使用同等难度材料、交叉顺序与必要间隔，控制学习效应；不能让同一律师先完整阅读同一卷宗再把第二次速度当成工具收益。模型 judge 可辅助筛查，但必须与人工金标准校准，并记录 judge 模型、prompt、版本与重复运行波动。

LawBench 混合分、检索 Recall@k/MRR、答案事实质量、工作流完成率、律师效率分别报告。当前 [85 分计划](../benchmarks/SCORE_85_PLAN.md) 属于独立模型实验工作流，其锚点组合结果不能替代一次应用盲测或本报告准入门槛。

### 6.3 性能、稳定性与恢复验证

建议容量实验采用 1千、1万、5万页的分档数据，以及 1、5、10 个并发用户；这些是待测阶梯，并非当前支持规模。记录设备、可用内存、OCR/LLM/embedding 版本、缓存状态与后台负载，分别测导入、重建索引、检索、模型生成和导出。

G1 建议初始目标：已建索引检索 p95≤2 秒；后台任务接收/状态查询 p95≤1 秒；重模型和 OCR 路径独立设预算；受支持负载下连续运行 8 小时无无法解释的任务遗失、数据不一致或持续资源增长。G2 延长稳定性验证，并在实际试点期间持续测量。

恢复目标建议 G1 为 RPO≤24 小时、RTO≤4 小时，即最多损失 24 小时内的新数据、4 小时内恢复可用；若业务不能接受，应在接入前升级保护方案。可评估 G2 达到 RPO≤1 小时、RTO≤1 小时，但必须有对应调度和演练证据。可用性目标根据客户工作时间定义分母与计划维护窗口，未收集足够周期数据前不承诺月度 SLA。

必须覆盖的故障包括：模型不可用/超时、Redis 断连、worker 或 Web 中断、磁盘满、数据库锁等待、原件丢失、备份损坏、checkpoint 缺失、重复投递、并发恢复、取消竞争、升级失败、权限撤销以及高耗时文件。记录恢复动作、遗留状态、数据一致性和总恢复时间。

## 7. 技术栈决策

| 层 | 当前建议 | 引入或替换条件 |
|---|---|---|
| API | 保留 FastAPI，逐步补契约和模块边界 | 依据维护成本拆分 router；响应版本策略不必局限于 URL 加 v1 |
| 数据迁移 | 补版本化迁移；可选明确的 SQL 迁移序列或 Alembic | 对当前原生 sqlite3 访问评估接入成本；异步驱动本身不能解决迁移可靠性 |
| 数据库 | G1/G2 优先验证 SQLite 的适用范围 | 写竞争、多实例或运维需求超过验证边界时评估 PostgreSQL；中文检索、分页、事务与恢复重新验收 |
| 向量检索 | 先测逐页评分瓶颈，再比较 sqlite-vec、LanceDB 等候选 | 固定候选版本，验证索引算法、过滤、删除更新、恢复和可分发性；使用向量扩展不自动意味着 ANN |
| 重排 | 用固定候选集测试本地 reranker | 质量增益超过延迟和资源代价，并在独立案件上确认后启用 |
| 文档解析 | 保留分级提取思路，建立格式/页级路由 | PaddleOCR、MinerU、Docling 与当前引擎同样本对照；比较表格、定位、漏检、资源及使用条件 |
| Agent | 保留共享业务 Agent，完善实际输入输出与版本记录 | Jinja2/instructor 是可选实现；仅当模板管理或结构输出需求明确时引入 |
| LangGraph | 保留可选运行时，依审核流程设计 interrupt | 审批权限、内容版本、恢复语义独立验收；不用覆盖率数字推导业务可靠性 |
| 队列 | 先统一任务状态和故障策略，按接管需求评估 arq 统一 | 迁移需验证幂等、租约、取消、授权上下文与重启收敛 |
| 观测 | 先补指标、关联 ID、告警与 runbook | Langfuse 可用于 prompt/trace，但先核对组件、资源、权限、脱敏和备份成本 |
| 数据保护 | 按资产选择设备/卷/文件/数据库保护与密钥管理 | SQLCipher 只覆盖相应数据库；原件、导出与备份单独设计 |
| 法条 | 继续权威来源、版本及哈希路线 | 外部种子库需核对出处、使用条件、时效与解析完整性；不凭条文数量直接采信 |
| 评测 | 保留现有审计协议，增加独立卷宗与人工金标准 | CLI/HTML 报告可改善使用体验；不改变指标分母或把失败删去 |
| CI | 保留离线门禁，验证目标环境后渐进扩大检查 | 安全扫描、依赖升级采用可处置流程；更新 PR 通过相关验证后再合入 |
| 前端 | 模块化、类型约束、浏览器回归和审阅状态优先 | Vue/React/Vite 依据团队与交互复杂度选择；SSE 根据体验需求排期 |
| 文档/部署 | 维护单一入口、发布说明、架构决策与恢复手册 | 文档站、Docker/Compose 按交付平台选择；明确宿主机模型服务连接与资源条件 |

SQLite 官方建议根据并发写、网络数据位置和多服务器需求选择客户端/服务器数据库，而非仅以用户数做判断。见 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)。

Langfuse 官方 Compose 指南把该方式用于本地或 VM 部署，并说明高可用、扩展与备份边界；其 VM 示例建议至少 4 核、16 GiB 内存。因此在与本地模型共用设备时必须先分配资源预算。见 [Langfuse 部署说明](https://langfuse.com/self-hosting/deployment/docker-compose)。

### 8.2 阶段放行检查
