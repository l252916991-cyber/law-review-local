# 信息隔离墙

设了隔离墙的案件，只有墙内名单上的人能看到，**管理员也不例外**。律所同时代理关联案件的对立方、或者新进律师曾在对方任职时，用它把相关的人挡在案件之外。墙外的人看到的效果和这个案件不存在一样。

## 谁能看到什么

| 身份 | 设墙案件 | 说明 |
| --- | --- | --- |
| 墙内名单上的人 | 正常访问 | 仍需原有的案件权限和角色，隔离墙只做减法 |
| 墙外的管理员 | 看不到 | 打开返回 404，与案件不存在相同；案件从列表、仪表盘计数和审计动态、成员名单、“我的任务”中消失 |
| 仍被分配到该案、但不在名单上的律师 | 看不到 | 案件分配不等于墙内身份 |
| 申请了破窗访问的管理员 | 限时可见 | 必须写明理由（至少 10 个字），有效 30 分钟，写入审计日志与安全事件 |
| 系统任务（启动、后台导入、索引重建） | 可见 | 没有请求身份时以系统身份执行 |

墙内名单按身份名称登记（与登录身份的名称一致）。成员改名后需要重新加入名单，在此之前按墙外处理：宁可拒绝，不会误放。

## 管理接口

只有管理员能操作；管理视图只显示案件编号、理由、名单和破窗记录，不显示案件标题，因为管理者自己可能在墙外。

```http
PUT    /api/case-walls/{case_id}              {"reason": "对方当事人由本所另案代理", "insiders": ["张律师", "李律师"]}
DELETE /api/case-walls/{case_id}?reason=关联案件已结案
POST   /api/case-walls/{case_id}/break-glass  {"reason": "客户投诉核查，需要核对材料归档情况"}
GET    /api/case-walls
```

设立、调整、撤除和破窗都会写入该案件的审计日志和安全事件。本机单人模式只有一个身份，分不出墙内墙外，设墙会被拒绝（409）。MCP 服务无法确认调用者身份，对设墙案件拒绝启动。目前没有界面，只能通过接口管理。

## 两层执行

**应用层（两种数据库都有）**：所有带案件编号的请求都经过 `require_case_access`，墙外直接返回 404；所有跨案件列出数据的地方（案件列表、归档列表、仪表盘、成员名单、我的任务）都会排除这些案件。

**数据库层（PostgreSQL）**：每个连接建立时写入当前身份（`lexvault.actor`，系统任务为 `lexvault.system=on`），并立即提交，防止后续回滚把身份清空。33 张表启用 `FORCE ROW LEVEL SECURITY`：

- 当前身份看不到的案件编号由 `lexvault_hidden_cases()` 算出，每条语句只算一次；
- 有 `case_id` 的表直接排除这些案件；
- 页、向量、消息、运行步骤等子表按主键回查父表，父表自己的策略照样生效，例如页查所属材料、向量查所属页；没有案件被隐藏时不回查；
- `scripts/generate_postgres_schema.py` 检查所有带案件关联列的表：没有归入受控或豁免名单的，生成直接失败，新表不会悄悄绕过隔离墙；
- 审计日志、安全事件、案件成员和隔离墙本身的表按设计不受行级策略约束：前两者是合规需要的完整记录，成员表在请求身份确定之前就要读取。展示审计内容的接口在应用层按墙过滤。

应用必须以**非超级用户**身份连接 PostgreSQL：超级用户和带 `BYPASSRLS` 属性的角色会绕过所有行级策略。建议让应用角色拥有业务表（`FORCE` 保证表的所有者同样受约束），由数据库管理员预先安装 pgvector。PostgreSQL 测试任务正是这样运行的：每个测试库都属于非超级用户角色 `lexvault_app`，全量测试都在行级策略生效的情况下通过。

## 证据

`tests/test_case_walls.py` 把种子演示案件设墙，在它的标题、每一页正文和一条证据里写入标记文本，然后：

- 以墙外管理员、仍被分配到该案的墙外律师两种身份，用该案件的各项编号请求**全部 GET 接口**，标记文本一次都没有出现；带案件编号的接口全部返回错误；
- 问答、工具调用、新增证据、修改证据全部被拒；
- 破窗访问必须写理由，生效后可以打开，过期后重新返回 404，审计和安全事件都有记录；撤墙后恢复原有权限；
- **只靠数据库**：在 PostgreSQL 上把应用层检查全部关掉，再做一遍全量遍历，标记依旧不出现，同时直接验证墙外身份读不到墙内的行、也写不进去。作为对照，同样关掉应用层检查后在 SQLite 上有 10 个 GET 接口泄露墙内内容（墙外管理员与墙外律师合计），说明这次遍历确实能发现泄露，PostgreSQL 上的干净结果来自数据库这一层。这个对照本身也是一个测试。

## 性能

10,000 页单案向量检索（[基准](../benchmarks/postgres-rls-overhead-20261102.md)）：超级用户 p50 51 ms；应用角色、没有案件被隐藏 67 ms；五分之四的材料对当前身份隐藏时 104 ms。结果与超级用户完全相同。子表策略最初写成"在父表的可见行里"，每条语句都要扫完整张父表，p50 达 347 ms；改成按主键回查后，开销只跟查询碰到的行数有关。

## 多租户

把“案件是否可见”换成“行属于哪个租户”，就是多租户隔离：每个连接写入租户编号，每张表按租户列加同样的策略，子表经父表判断，再用同一个生成器检查保证新表不会遗漏。本项目按设计是一个律所一套实例，没有做多租户，但这套机制可以直接迁移过去。

## 边界

- SQLite 部署只有应用层这一道防线。
- LangGraph 断点记录是本机 SQLite 文件，不受行级策略约束；通过接口读取运行记录时仍经过应用层检查。
- 唯一约束冲突之类的错误理论上可以让墙外的人推断某行存在，但读不到任何内容。
